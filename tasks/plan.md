# Implementation Plan: biohucker

Источник требований: [SPEC.md](../SPEC.md) и `SPEC-<module>.md`. Задачи с критериями
приёмки и проверками лежат в [todo.md](todo.md).

## Overview

Строим локальное веб-приложение: ежедневный чек-ин в чате → поиск связей → недельный
эксперимент из библиотеки → честный отчёт. Работа идёт вертикальными срезами. После
каждой фазы приложение запускается и умеет на один пользовательский сценарий больше.

```
Фаза 0  каркас + LLM-ядро        → приложение стартует, цикл tool use проверен на FakeLLM
Фаза 1  дневник через форму      → можно вести дневник без LLM  (первая польза)
Фаза 2  чек-ин в чате            → основной ежедневный сценарий
Фаза 3  история и связи          → правка записей, графики, «Связи»
Фаза 4  эксперименты             → полный недельный цикл с отчётом
```

**Строго последовательно:** T6 → T7; T14 → T15 → T16.

## Architecture Decisions

1. **Самый рискованный кусок идёт первым.** Неизвестно, умеет ли бесплатная
   `google/gemma-4-26b-a4b-it:free` в tool use. Поэтому LLM-клиент и скрипт проверки
   (`scripts/smoke_llm.py`) — это T2–T3, до любой фичи. Из контейнера разработки
   OpenRouter недоступен, так что скрипт запускает пользователь у себя. Если tool
   use не работает, перед T6 меняем стратегию: просим у модели JSON в тексте и
   парсим его pydantic'ом. Интерфейс `LLMClient.run` при этом не меняется.
2. **Первая польза — без LLM.** Форма чек-ина (T5) появляется раньше чата. Она же
   остаётся запасным путём при `degraded` (Success Criteria №6).
3. **Две семантики записи.** Чат делает `upsert`: частичный, `None` не затирает
   сохранённое. Правка из истории делает `replace`: запись целиком, чтобы можно
   было очистить поле. В SPEC-journal описан только `upsert`, поэтому `replace`
   добавляется в спеку в T9.
4. **Модель ничего не пишет в БД.** Инструмент `propose_checkin` кладёт черновик в
   память, а сохраняет код по кнопке. Состояние чата и черновика хранится в памяти
   процесса (один пользователь, локально).
5. **Статистика и отчёт — чистые функции** (`insights.find_insights`,
   `experiments.build_report`). Их тестируем таблицами граничных случаев без БД и LLM.
6. **Эвалы пишутся, но не запускаются агентом.** T8 и T17 создают сценарии с маркером
   `eval`. По умолчанию `pytest` их исключает (`addopts = -m "not eval"`), а запускает
   пользователь (Boundaries: Ask first).
7. **Зависимости** (полный список, сверх него — только с вопросом): `fastapi`,
   `uvicorn[standard]`, `jinja2`, `python-multipart`, `sqlmodel`, `openai`, `pyyaml`,
   `python-dotenv`; dev — `pytest`, `ruff`, `httpx`. HTMX и Chart.js подключаются
   с CDN с фиксированной версией.

## Risks and Mitigations

| Риск | Влияние | Митигация |
|---|---|---|
| Gemma free не делает tool calls или делает их криво | High | T3 smoke-скрипт до фич; fallback на JSON-в-тексте за тем же интерфейсом; повторная попытка с ошибкой валидации |
| Лимиты free-tier (429) | Med | ≤ 4 запросов на чек-ин; `degraded` → форма; один повтор через 2 с |
| Из контейнера нет доступа к OpenRouter, живую модель агент не проверит | Med | Все тесты на FakeLLM/MockTransport; живые проверки — чекпоинты пользователя |
| На первой неделе связей почти никогда не будет (строгий порог) | Low (так задумано) | UI объясняет «нужно больше дней»; тест на синтетике доказывает, что настоящая связь находится |
| Неточные источники в библиотеке советов | Med | T12: только советы с конкретным эпизодом/статьёй; сомнительные не включаются |
| Время «лёг» после полуночи / AM-PM путаница | Med | Правило 2–16 ч в T4 + тесты; агент переспрашивает |
| Токены на эвалы (урок из поста) | Med | Эвалы только вручную; повтор только упавших сценариев |
