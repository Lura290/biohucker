# Spec: biohucker — личный агент-биохакер

> Статус: **утверждён** (открытые вопросы закрыты). Модульные спеки — `SPEC-<module>.md`.

## Objective

**Зачем.** Долгосрочная цель пользователя — биологический возраст на 5 лет меньше
паспортного. Агент работает **только с привычками**: сон, утренний свет, движение,
тренировки. Каждая привычка проверяется на себе маленькими экспериментами.
Измерение биовозраста (анализы, PhenoAge) — сознательно вне продукта.

**Пользователь.** Один человек, сам автор. Без регистрации и без нескольких аккаунтов.

**Основной цикл:**

```
каждый день: чек-ин в чате (~1 мин)
   │
   ▼ ≥ 7 дней записей
неделя-база: агент ищет связи в записях
   │
   ▼
агент предлагает 1 эксперимент на неделю из библиотеки советов
   │  пользователь принимает / отклоняет
   ▼
неделя эксперимента: чек-ины продолжаются, плюс отметка «выполнил эксперимент»
   │
   ▼
отчёт: честное сравнение «до» и «во время» → следующий эксперимент
```

### User stories

1. **Ежедневный чек-ин.** Я открываю веб-приложение. Если за сегодня нет записи,
   агент сам начинает чат и коротко спрашивает:
   - во сколько лёг и во сколько встал;
   - энергия (1–10);
   - настроение (1–10);
   - была ли утренняя прогулка (да/нет и сколько минут);
   - сколько шагов;
   - была ли тренировка (да/нет, тип, длительность).

   Я могу ответить одной фразой («лёг в 23:40, встал в 7:10, энергия 6…»).
   Агент сам разбирает её и переспрашивает только то, чего не хватает. Перед
   сохранением агент показывает итог записи, и я её подтверждаю.
2. **Правка.** Я могу исправить или удалить запись за любой день.
3. **Связи.** Когда накопилось не меньше 7 записей, агент показывает найденные
   связи, например «в дни с утренней прогулкой энергия в среднем на 1.4 выше».
   Агент указывает силу связи и сколько дней за ней стоит и не выдаёт связь за
   причину.
4. **Эксперимент.** Агент предлагает **один** эксперимент из библиотеки. Выбор
   опирается на найденные связи и на то, что я ещё не пробовал. У эксперимента
   есть название, протокол, источник (например, Huberman Lab, эпизод N), целевая
   метрика и длительность 7 дней. Я принимаю его или прошу другой.
5. **Отчёт.** По окончании эксперимента я вижу сравнение базовой недели и недели
   эксперимента по целевой и остальным метрикам, сколько дней эксперимент реально
   выполнялся и вывод одного из трёх видов: «есть эффект», «в пределах шума»,
   «данных мало».
6. **История.** Я вижу таблицу/графики своих записей и список прошедших
   экспериментов с итогами.

### Честность (жёсткие правила продукта)

- Агент **не утверждает**, что изменил биологический возраст: он его не измеряет.
- Вывод «есть эффект» допускается, только если разница по целевой метрике больше
  разброса базовой недели (|Δ среднего| > SD базы) **и** эксперимент выполнялся
  в ≥ 5 из 7 дней. Если дней с данными < 5 в любой из недель, вывод — «данных мало».
  Иначе вывод — «в пределах шума».
- Корреляции считаются только по дням, где есть обе метрики, и только если таких
  дней ≥ 7. В каждой показанной связи указаны n и формулировка «связь, не причина».
- Советы берутся **только из библиотеки** (`experiments/library.yaml`). LLM
  выбирает и объясняет их, но не придумывает новые протоколы.
- Агент не даёт медицинских рекомендаций. Не ставит диагнозы, не советует
  лекарства и рецептурные препараты, не называет дозировки добавок. Если
  пользователь жалуется на здоровье, агент советует обратиться к врачу.

## Tech Stack

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | задано |
| Веб | FastAPI + Jinja2-шаблоны + HTMX | весь проект на Python, без отдельного фронтенд-сборщика; легко тестировать через `TestClient` |
| LLM | OpenRouter (OpenAI-совместимый API) через пакет `openai` с `base_url=https://openrouter.ai/api/v1`, tool use | задано |
| Хранение | SQLite (файл `data/biohucker.db`) через SQLModel | бесплатно, ноль инфраструктуры, один файл легко бэкапить |
| Статистика | стандартная библиотека `statistics` (+ ранговая корреляция Спирмена, своя реализация ~20 строк) | без тяжёлых зависимостей вроде pandas/scipy |
| Графики | Chart.js с CDN на странице истории | без сборки |
| Окружение | `uv` (зависимости, запуск), `ruff` (линт + формат), `pytest` | быстрые стандартные инструменты |

Конфигурация через переменные окружения (`.env`, в git не попадает):
`OPENROUTER_API_KEY`, `OPENROUTER_MODEL` (по умолчанию `google/gemma-4-31b-it:free`),
`DATABASE_URL` (по умолчанию `sqlite:///data/biohucker.db`).

**Запуск только локально** (`127.0.0.1`), без авторизации и хостинга.

**Риски бесплатной модели:**
- *Лимиты free-tier OpenRouter* (запросов в минуту и в день). Чек-ин должен
  укладываться в ≤ 4 запроса к модели. При ошибке 429 или недоступности показывается
  запасная форма (Success Criteria №6).
- *Надёжность tool use.* Поддержку tool calls у модели проверить заранее не удалось.
  Модуль `llm` проверяет ответ: если модель вернула текст вместо tool call или
  невалидные аргументы, делается одна повторная попытка с подсказкой об ошибке
  валидации, затем — запасная форма. В БД без валидации не пишется ничего.

## Commands

```bash
uv sync                                   # установить зависимости
uv run uvicorn biohucker.web.app:app --reload   # dev-сервер на http://127.0.0.1:8000
uv run pytest                             # unit + интеграционные тесты (без сети, LLM подменён)
uv run pytest -m eval                     # LLM-эвалы на реальной модели (ручной запуск, тратит токены)
uv run ruff check . && uv run ruff format --check .   # линт и формат
```

## Project Structure

```
biohucker/
  journal/        → модель дневной записи, валидация, хранилище (SQLite)
  llm/            → клиент OpenRouter, цикл tool use, FakeLLM для тестов
  checkin/        → агент чек-ина: промпт, инструменты, диалог
  insights/       → поиск связей в записях (чистая статистика, без LLM)
  experiments/    → library.yaml, выбор эксперимента, жизненный цикл, отчёт «до/во время»
  web/            → FastAPI-приложение, роуты, шаблоны, статика
tests/            → зеркалит структуру пакета: tests/journal/, tests/insights/, …
evals/            → сценарии LLM-эвалов (маркер pytest `eval`)
data/             → файл SQLite (в .gitignore)
SPEC.md, SPEC-<module>.md, tasks/plan.md, tasks/todo.md
```

## Code Style

```python
from datetime import date, time

from pydantic import BaseModel, Field


class CheckinEntry(BaseModel):
    """Одна дневная запись. Все поля, кроме дня, опциональны: лучше частичная запись, чем никакой."""

    day: date
    bedtime: time | None = None
    wake_time: time | None = None
    energy: int | None = Field(default=None, ge=1, le=10)
    mood: int | None = Field(default=None, ge=1, le=10)
    morning_walk_min: int | None = Field(default=None, ge=0, le=300)
    steps: int | None = Field(default=None, ge=0, le=100_000)
    workout: str | None = None  # "сила 45 мин"; None — тренировки не было
```

- Типы на всех публичных функциях; pydantic-модели на границах модулей (в том числе
  аргументы инструментов LLM).
- Бизнес-логика — чистые функции без I/O (`insights`, отчёт эксперимента).
  I/O только в `journal` (БД), `llm` (сеть) и `web`.
- Имена в коде на английском, тексты интерфейса и промпты на русском.
- `ruff` с настройками по умолчанию + сортировка импортов; длина строки 100.

## Testing Strategy

| Уровень | Что покрывает | Инструмент |
|---|---|---|
| Unit | валидация записи, статистика связей, правила вердикта отчёта, выбор эксперимента из библиотеки | `pytest`, без сети |
| Integration | хранилище на временной SQLite; веб-роуты через `TestClient`; цикл tool use агента с `FakeLLM`, который возвращает заранее заданные tool calls | `pytest`, без сети |
| LLM-эвалы | ~10 сценариев: разбор свободного ответа в запись, переспрос недостающих полей, отказ давать медсоветы, объяснение эксперимента без выдумок | `pytest -m eval`, реальная модель, запуск вручную |

- Правила вердикта (раздел «Честность») покрыты unit-тестами на граничных случаях,
  включая n < 5, ровно 5 дней и |Δ| = SD.
- **Бюджет эвалов:** эвалы не запускаются автоматически в `/build` и `/test`, их
  запускает только пользователь. Если эвал упал, сначала чинится детерминированная
  часть (схемы, сигнатуры инструментов), а повторный прогон делается только по
  упавшим сценариям. Это урок из поста: из-за мелочи весь LLM-judge
  перезапускался заново.
- Новый код без тестов не мержится; падающие тесты не удаляются и не скипаются.

## Boundaries

- **Always:** гонять `uv run pytest` и `ruff` перед каждым коммитом; валидировать
  всё, что пришло от LLM, через pydantic, прежде чем писать в БД; показывать
  пользователю итог записи перед сохранением; держать советы только в `library.yaml`
  с источником (агент составляет библиотеку сам; совет без конкретного
  источника в неё не попадает).
- **Ask first:** новые зависимости сверх списка в Tech Stack; изменение схемы БД
  после появления реальных данных; запуск `pytest -m eval`; смена модели по
  умолчанию.
- **Never:** коммитить `.env`, ключи и файл БД; давать медицинские советы, дозировки
  и рекомендации лекарств; утверждать причинность по корреляции; выдавать «есть
  эффект» в нарушение правил из раздела «Честность»; отправлять данные дневника
  куда-либо, кроме выбранной LLM-модели в OpenRouter.

## Success Criteria

1. Чек-ин из одной фразы со всеми полями сохраняется за ≤ 2 реплики агента; при
   неполном ответе агент спрашивает только недостающие поля.
2. Невалидные значения (энергия 12, отрицательные шаги) не попадают в БД, а агент
   переспрашивает.
3. Если за 7 дней дневника есть связь, раздел «Связи» показывает её с n и силой.
   Если связей нет, он честно пишет «явных связей нет».
4. Предложенный эксперимент всегда существует в `library.yaml` (проверяется
   тестом), и за 30 дней не повторяется уже отклонённый или пройденный.
5. Отчёт выдаёт вердикт строго по правилам из раздела «Честность» (unit-тесты на
   граничные случаи).
6. Приложение запускается одной командой, работает без интернета для всего, кроме
   LLM-чата; при недоступности OpenRouter чек-ин можно заполнить обычной формой.
7. `uv run pytest` зелёный и не требует сети и API-ключа.

## Capability Map

| Module id | Ответственность | Зависит от |
|---|---|---|
| `journal` | Модель дневной записи, валидация, CRUD в SQLite | — |
| `llm` | Клиент OpenRouter, цикл tool use, `FakeLLM` для тестов | — |
| `checkin` | Агент ежедневного опроса: промпт, инструменты `propose_checkin`/`get_today_context`, разбор свободного ответа | `journal`, `llm` |
| `insights` | Поиск связей между метриками (Спирмен, минимальное n, текстовая формулировка) | `journal` |
| `experiments` | Библиотека советов, выбор эксперимента, жизненный цикл (предложен → активен → завершён), отчёт «до/во время» с вердиктом | `journal`, `insights`, `llm` |
| `web` | Страницы: чат, история с графиками, эксперименты; запасная форма чек-ина | все выше |

Порядок сборки: `journal`, `llm` → `checkin` → `insights` → `experiments`.
Модуль `web` растёт **вертикальными срезами** вместе с каждым модулем: после
`checkin` уже есть рабочая страница чата, а не всё приложение в конце.

## Решения по открытым вопросам

| Вопрос | Решение |
|---|---|
| Модель | `google/gemma-4-31b-it:free` (см. риски в Tech Stack) |
| «Раз в день» | чек-ин стартует при открытии страницы, если за сегодня нет записи; напоминаний в v1 нет |
| Где работает | только локально, SQLite |
| Биовозраст | не делаем, только привычки |
| Библиотека советов | ~15 советов собирает агент, у каждого обязателен источник; отдельного ревью нет |
| Доп. запреты | нет, достаточно Boundaries |
