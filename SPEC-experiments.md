# Spec: experiments

Карта: [SPEC.md → Capability Map](SPEC.md#capability-map). Зависит от: `journal`, `insights`, `llm`.

## Objective

Предложить один недельный эксперимент из проверенной библиотеки, провести его и честно
сравнить неделю «до» с неделей «во время».

## Библиотека — `biohucker/experiments/library.yaml`

```yaml
- id: morning-sunlight
  title: Утренний свет
  protocol: 10–20 минут на улице в первый час после подъёма, без солнцезащитных очков.
  target_metric: energy          # energy | mood | sleep_hours
  done_question: Был на улице 10+ минут в первый час после подъёма?
  source: "Huberman Lab, «Using Light for Health» (2022)"
  contraindications: []          # текстовые оговорки, если есть
```

- ~15 советов: сон, свет, движение, кофеин, дыхание/NSDR, холод, зона 2. Каждый с
  **конкретным источником**: подкаст с эпизодом, статья или книга.
- Без добавок, препаратов и дозировок (Boundaries в SPEC.md).
- Тест: каждый элемент проходит схему, `id` уникальны, `source` не пустой.

## Жизненный цикл

```
suggested ──accept──▶ active (7 дней) ──▶ finished (+отчёт)
    │                    │
  reject              abandon
```

Одновременно не больше одного `suggested`/`active`. Таблица `experiments`: `id`,
`library_id`, `status`, `start_day`, `end_day`, `baseline_start`, `report_json`.

## Выбор эксперимента

1. Кандидаты: библиотека минус пройденные и отклонённые за последние 30 дней.
2. Ранжирование **кодом**: выше советы, чей `target_metric` совпадает с исходом из
   найденных `insights` или с самой «проседающей» метрикой базовой недели.
3. LLM получает топ-3 кандидата и инсайты и **выбирает id из этих трёх** плюс пишет
   2–3 предложения, почему именно он. Если id не из списка или `degraded`, берётся топ-1
   с шаблонным объяснением.

Условие старта: ≥ 7 записей за последние 10 дней (базовая неделя).

## Отчёт «до / во время»

- База: 7 дней до `start_day`. Эксперимент: `start_day … start_day+6`.
- Для каждой метрики: среднее, SD, n в обеих неделях, Δ среднего.
- `adherence` = число дней с `experiment_done = true`.
- **Вердикт** по целевой метрике (правила из SPEC.md → Честность):
  - `insufficient_data` — n < 5 в любой неделе **или** adherence < 5;
  - `effect` — |Δ| > SD базы (а если SD базы = 0, то |Δ| ≥ 1);
  - `noise` — иначе.
  Направление эффекта показывается всегда: «лучше» или «хуже».
- Текст отчёта собирается шаблоном. LLM отчёт не пишет, чтобы не приукрашивать.

## Acceptance Criteria

1. Предложенный `library_id` всегда есть в библиотеке и не отклонён за последние 30 дней.
2. Меньше 7 базовых записей → предложения нет, вместо него «нужно ещё N дней».
3. Граничные случаи вердикта покрыты тестами: adherence 4/5, n 4/5, |Δ| = SD, SD = 0.
4. Отчёт формируется автоматически при первом открытии приложения после `end_day`.
5. Отказ от эксперимента возвращает к выбору следующего.

## Тесты

Unit: схема библиотеки, ранжирование, `build_report`. Integration: жизненный цикл на SQLite и
`FakeLLM` (включая выбор id не из списка). Эвал: объяснение выбора не содержит фактов,
которых нет в `protocol`/`source`.
